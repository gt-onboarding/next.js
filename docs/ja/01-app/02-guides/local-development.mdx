Next.js は、優れた開発者体験を提供するように設計されています。アプリケーションが大きくなるにつれて、ローカル開発中のコンパイルにかかる時間が長くなってきたと感じることがあるかもしれません。このガイドでは、よくあるコンパイル時のパフォーマンス問題を特定し、解決する方法を説明します。

## ローカル開発と本番環境

`next dev` を使った開発プロセスは、`next build` や `next start` の場合とは異なります。

`next dev` は、アプリケーション内のルートを、開いたりナビゲーションしたりしたタイミングでコンパイルします。これにより、アプリケーション内のすべてのルートがコンパイルされるのを待つことなく開発サーバーを起動でき、より高速でメモリ使用量も少なくなります。本番ビルドを実行する場合は、ファイルの圧縮（minify）やコンテンツハッシュの作成といった、ローカル開発では不要なその他の最適化が適用されます。

## ローカル開発環境のパフォーマンス改善

### 1. コンピューターのウイルス対策ソフトを確認する

ウイルス対策ソフトはファイルアクセスを遅くすることがあります。これは特に Windows マシンでよく起こりますが、ウイルス対策ツールがインストールされているあらゆるシステムで発生する可能性があります。

Windows では、プロジェクトを [Microsoft Defender Antivirus の除外リスト](https://support.microsoft.com/en-us/windows/virus-and-threat-protection-in-the-windows-security-app-1362f4cd-d71a-b52a-0b66-c2820032b65e#bkmk_threat-protection-settings)に追加できます。

1. **「Windows セキュリティ」** アプリを開き、**「ウイルスと脅威の防止」** &rarr; **「設定の管理」** &rarr; **「除外の追加または削除」** を選択します。
2. **「フォルダー」** の除外を追加し、プロジェクトフォルダーを選択します。

macOS では、ターミナルから [Gatekeeper](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web) を無効化できます。

1. ターミナルで `sudo spctl developer-mode enable-terminal` を実行します。
2. **「システム設定」** アプリを開き、**「プライバシーとセキュリティ」** &rarr; **「開発者ツール」** を選択します。
3. 使用しているターミナルが一覧に表示され、有効になっていることを確認します。iTerm や Ghostty のようなサードパーティ製ターミナルを使用している場合は、それも一覧に追加します。
4. ターミナルを再起動します。

### 2. Next.js をアップデートして Turbopack を使用する

最新バージョンの Next.js を使用していることを確認してください。多くの場合、新しいバージョンではパフォーマンスが改善されています。

Turbopack は現在、Next.js の開発環境におけるデフォルトのバンドラであり、webpack と比較して大幅なパフォーマンス向上を実現します。

```bash package="pnpm"
pnpm add next@latest
pnpm dev  # Turbopackはデフォルトで使用されます
```

```bash package="npm"
npm install next@latest
npm run dev  # Turbopackがデフォルトで使用されます
```

```bash package="yarn"
yarn add next@latest
yarn dev  # Turbopackがデフォルトで使用されます
```

```bash package="bun"
bun add next@latest
bun dev  # Turbopackがデフォルトで使用されます
```

Turbopack の代わりに Webpack を使用する必要がある場合は、Webpack を選択することもできます。

```bash package="pnpm"
pnpm dev --webpack
```

```bash package="npm"
npm run dev -- --webpack
```

```bash package="yarn"
yarn dev --webpack
```

```bash package="bun"
bun run dev --webpack
```

[Turbopack の詳細](/blog/turbopack-for-development-stable)をご覧ください。詳細は、[アップグレードガイド](/docs/app/guides/upgrading)や codemod なども参照してください。

### 3. インポートを確認する

コードのインポート方法は、コンパイルやバンドルにかかる時間に大きく影響します。[パッケージバンドルの最適化](/docs/app/guides/package-bundling) について詳しく学び、[Dependency Cruiser](https://github.com/sverweij/dependency-cruiser) や [Madge](https://github.com/pahen/madge) などのツールも活用してみてください。

#### アイコンライブラリ

`@material-ui/icons`、`@phosphor-icons/react`、`react-icons` のようなライブラリでは、実際には一部のアイコンしか使っていなくても、何千ものアイコンがインポートされてしまう可能性があります。必要なアイコンだけを個別にインポートするようにしましょう。

```jsx
// こうではなく:
import { TriangleIcon } from '@phosphor-icons/react'

// こうする:
import { TriangleIcon } from '@phosphor-icons/react/dist/csr/Triangle'
```

使用しているアイコンライブラリのドキュメントに、どのようなインポートパターンを使うべきかが記載されていることが多いです。次の例は、[`@phosphor-icons/react`](https://www.npmjs.com/package/@phosphor-icons/react#import-performance-optimization) の推奨に従ったものです。

`react-icons` のようなライブラリには、多くの異なるアイコンセットが含まれています。1つのセットを選び、そのセットに統一してください。

たとえば、アプリケーションで `react-icons` を使っていて、次のすべてをインポートしているとします:

- `pi` (Phosphor Icons)
- `md` (Material Design Icons)
- `tb` (tabler-icons)
- `cg` (cssgg)

これらを組み合わせると、コンパイラが扱わなければならないモジュールは合計で数万単位になり、各セットから1つずつしかインポートを使っていなくても同様です。

#### バレルファイル

「バレルファイル」とは、他のファイルから多数の値をまとめて再エクスポートするファイルのことです。コンパイラは、`import` 時にモジュールスコープに副作用がないかを確認するためにそれらをパースする必要があるため、ビルドが遅くなる可能性があります。

可能な場合は、特定のファイルから直接インポートするようにしてください。バレルファイルと Next.js に組み込まれている最適化については、[こちら](https://vercel.com/blog/how-we-optimized-package-imports-in-next-js)を参照してください。

#### パッケージのインポートを最適化する

Next.js は、特定のパッケージに対してインポートを自動的に最適化できます。バレルファイル（barrel file）を利用するパッケージを使用している場合は、それらを `next.config.js` に追加してください。

```jsx
module.exports = {
  experimental: {
    optimizePackageImports: ['package-name'],
  },
}
```

Turbopack はインポートを自動解析して最適化します。このような設定は必要ありません。

### 4. Tailwind CSS のセットアップを確認する

Tailwind CSS を使用している場合は、正しく設定されていることを確認してください。

よくある間違いとして、`content` 配列に `node_modules` など、本来スキャンすべきでない大きなディレクトリを含めてしまう設定があります。

Tailwind CSS バージョン 3.4.8 以降では、ビルドを遅くする可能性がある設定について警告が表示されます。

1. `tailwind.config.js` では、どのファイルをスキャンするかを明確に指定してください:

   ```jsx
   module.exports = {
     content: [
       './src/**/*.{js,ts,jsx,tsx}', // 良い例
       // これは範囲が広すぎる可能性があります
       // `packages/**/node_modules` もマッチしてしまいます
       // '../../packages/**/*.{js,ts,jsx,tsx}',
     ],
   }
   ```

2. 不要なファイルをスキャンしないようにしてください:

   ```jsx
   module.exports = {
     content: [
       // より良い例 - 'src' フォルダのみをスキャンします
       '../../packages/ui/src/**/*.{js,ts,jsx,tsx}',
     ],
   }
   ```

### 5. カスタム webpack 設定を確認する

独自の webpack 設定を追加している場合、それがコンパイルを遅くしている可能性があります。

ローカル開発で本当にそれらが必要かどうかを検討してください。特定のツールは本番ビルドでのみ有効にするようにしたり、代わりにデフォルトの Turbopack バンドラーを使用して [loaders](/docs/app/api-reference/config/next-config-js/turbopack#configuring-webpack-loaders) を設定することも検討できます。

### 6. メモリ使用量の最適化

アプリが非常に大規模な場合、より多くのメモリが必要になる場合があります。

[メモリ使用量の最適化について詳しく見る](/docs/app/guides/memory-usage)

### 7. サーバーコンポーネントとデータフェッチ

サーバーコンポーネントを変更すると、その変更内容を反映するためにローカルでページ全体が再レンダーされ、その際にコンポーネント用の新しいデータ取得も行われます。

実験的な `serverComponentsHmrCache` オプションを使用すると、ローカル開発環境における Hot Module Replacement (HMR) のリフレッシュ間で、サーバーコンポーネント内の `fetch` レスポンスをキャッシュできます。これにより、レスポンスが高速化され、従量課金される API 呼び出しのコストを削減できます。

[実験的なオプションの詳細](/docs/app/api-reference/config/next-config-js/serverComponentsHmrCache)をご覧ください。

### 8. Docker よりローカル開発を検討する

Mac や Windows での開発に Docker を使用している場合、Next.js をローカルで実行する場合と比べて、パフォーマンスが大幅に低下することがあります。

Mac や Windows 上での Docker のファイルシステムアクセスが原因で、Hot Module Replacement (HMR) に数秒から数分かかる場合がありますが、同じアプリケーションでもローカルで開発すると HMR は高速に動作します。

このパフォーマンス差は、Linux 以外の環境で Docker がファイルシステム操作を扱う方法に起因します。最良の開発体験のために、次の点を検討してください:

- 開発では Docker の代わりにローカル開発（`npm run dev` または `pnpm dev`）を使用する
- Docker は本番デプロイや本番ビルドのテストに限定して使用する
- 開発で Docker を使わざるを得ない場合は、Linux マシンまたは VM 上で Docker を利用することを検討する

本番利用向けの [Docker デプロイの詳細](/docs/app/getting-started/deploying#docker) を確認してください。

## 問題を特定するためのツール

### fetch の詳細ログ

開発中に何が起きているかをより詳しく確認するには、`next.config.js` ファイルで `logging.fetches` オプションを使用します。

```js
module.exports = {
  logging: {
    fetches: {
      fullUrl: true,
    },
  },
}
```

[fetch のログ出力について詳しくはこちら](/docs/app/api-reference/config/next-config-js/logging).

### Turbopack トレース

Turbopack トレースは、ローカル開発中のアプリケーションのパフォーマンスを把握するのに役立つツールです。
各モジュールのコンパイルにかかった時間や、それらの関連性に関する詳細な情報を提供します。

1. 最新バージョンの Next.js がインストールされていることを確認します。
1. Turbopack のトレースファイルを生成します:

   ```bash package="pnpm"
   NEXT_TURBOPACK_TRACING=1 pnpm dev
   ```

   ```bash package="npm"
   NEXT_TURBOPACK_TRACING=1 npm run dev
   ```

   ```bash package="yarn"
   NEXT_TURBOPACK_TRACING=1 yarn dev
   ```

   ```bash package="bun"
   NEXT_TURBOPACK_TRACING=1 bun dev
   ```

1. アプリケーション内を操作するか、問題を再現できるようにファイルを編集します。
1. Next.js の開発サーバーを停止します。
1. `.next/dev` フォルダー内に `trace-turbopack` というファイルが生成されます。
1. `npx next internal trace [path-to-file]` を使ってファイルを解析できます:

   ```bash
   npx next internal trace .next/dev/trace-turbopack
   ```

   `trace` が利用できないバージョンでは、コマンド名は `turbo-trace-server` です:

   ```bash
   npx next internal turbo-trace-server .next/dev/trace-turbopack
   ```

1. トレースサーバーが起動したら、https://trace.nextjs.org/ でトレースを表示できます。
1. デフォルトではトレースビューアは処理時間を集計表示します。個々の計測時間を確認するには、ビューア右上の "Aggregated in order" を "Spans in order" に切り替えます。

> **補足**: トレースファイルは開発サーバーのディレクトリ配下に配置されます。デフォルトでは `.next/dev` です。

### それでも問題が解決しない場合

[Turbopack Tracing](#turbopack-tracing) セクションで生成されたトレースファイルを用意し、[GitHub Discussions](https://github.com/vercel/next.js/discussions) または [Discord](https://nextjs.org/discord) に投稿してください。
