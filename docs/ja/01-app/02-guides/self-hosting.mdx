Next.js アプリを[デプロイ](/docs/app/getting-started/deploying)する際には、利用しているインフラストラクチャに応じて、さまざまな機能をどのように扱うかを設定する必要が出てくることがあります。

## リバースプロキシ

セルフホスティングする場合は、Next.js サーバーをインターネットに直接公開するのではなく、その前段に nginx のようなリバースプロキシを配置することを推奨します。リバースプロキシは、形式不正なリクエスト、低速接続攻撃、ペイロードサイズの制限、レート制限、その他のセキュリティ上の懸念点を処理し、これらのタスクを Next.js サーバーからオフロードすることができます。これにより、サーバーはリクエストの検証ではなくレンダリングにリソースを割り当てることができます。

## 画像最適化

`next/image` を使った[画像最適化](/docs/app/api-reference/components/image)は、`next start` を使ってデプロイする場合、セルフホスト環境でも追加の設定なしで動作します。画像の最適化を別サービスに任せたい場合は、[image loader を設定](/docs/app/api-reference/components/image#loader)できます。

画像最適化は、`next.config.js` でカスタム image loader を定義することで、[静的エクスポート](/docs/app/guides/static-exports#image-optimization)でも利用できます。画像はビルド時ではなく、ランタイムに最適化される点に注意してください。

> **補足:**
>
> - glibc ベースの Linux システムでは、過剰なメモリ使用を防ぐために、画像最適化に[追加の設定](https://sharp.pixelplumbing.com/install#linux-memory-allocator)が必要になる場合があります。
> - [最適化された画像のキャッシュ動作](/docs/app/api-reference/components/image#minimumcachettl)と TTL の設定方法について確認できます。
> - [画像最適化を無効にする](/docs/app/api-reference/components/image#unoptimized)こともでき、その場合でも `next/image` を使うその他の利点は維持されます。例えば、画像を別途自前で最適化している場合などです。

## Proxy

[Proxy](/docs/app/api-reference/file-conventions/proxy) は、`next start` を使ってデプロイするセルフホスト環境では、追加の設定なしで動作します。受信リクエストへのアクセスが必要なため、[静的エクスポート](/docs/app/guides/static-exports)ではサポートされません。

Proxy は [Edge ランタイム](/docs/app/api-reference/edge)を使用します。これは利用可能な Node.js API のサブセットであり、アプリケーション内のあらゆるルートやアセットの手前で実行される可能性があるため、低レイテンシを確保するのに役立ちます。これを避けたい場合は、[フル Node.js ランタイム](/blog/next-15-2#nodejs-middleware-experimental)を使用して Proxy を実行できます。

すべての Node.js API を必要とするロジックを追加したい場合（または外部パッケージを使用したい場合）、そのロジックを [layout](/docs/app/api-reference/file-conventions/layout) 内の[サーバーコンポーネント](/docs/app/getting-started/server-and-client-components)に移動できる場合があります。たとえば、[headers](/docs/app/api-reference/functions/headers) をチェックしたり、[リダイレクト](/docs/app/api-reference/functions/redirect)を行ったりするケースです。また、`next.config.js` を通じて、ヘッダー、Cookie、クエリパラメータを使用して [redirect](/docs/app/api-reference/config/next-config-js/redirects#header-cookie-and-query-matching) や [rewrite](/docs/app/api-reference/config/next-config-js/rewrites#header-cookie-and-query-matching) を行うこともできます。それでも実現できない場合は、[カスタムサーバー](/docs/pages/guides/custom-server)を使用することもできます。

## 環境変数

Next.js は、ビルド時と実行時の両方の環境変数をサポートしています。

**デフォルトでは、環境変数はサーバーでのみ利用可能です。** 環境変数をブラウザに公開するには、`NEXT_PUBLIC_` というプレフィックスを付ける必要があります。ただし、これらの公開環境変数は、`next build` の実行時に JavaScript バンドルへインライン展開されます。

<PagesOnly>

実行時の環境変数を読み取るには、`getServerSideProps` を使うか、[App Router を段階的に採用](/docs/app/guides/migrating/app-router-migration)することを推奨します。

</PagesOnly>

<AppOnly>

動的レンダリング中にサーバー上で安全に環境変数を読み取ることができます。

```tsx filename="app/page.ts" switcher
import { connection } from 'next/server'

export default async function Component() {
  await connection()
  // cookies、headers、その他の Dynamic API も
  // 動的レンダリングの対象となるため、
  // この環境変数は実行時に評価される
  const value = process.env.MY_VALUE
  // ...
}
```

```jsx filename="app/page.js" switcher
import { connection } from 'next/server'

export default async function Component() {
  await connection()
  // cookies、headers、その他の Dynamic API も
  // 動的レンダリングの対象となるため、
  // この環境変数は実行時に評価される
  const value = process.env.MY_VALUE
  // ...
}
```

</AppOnly>

これにより、異なる値を持つ複数の環境間で昇格させて利用できる、単一の Docker イメージを使用できます。

> **補足:**
>
> - [`register` 関数](/docs/app/guides/instrumentation)を使用して、サーバーの起動時にコードを実行できます。

## キャッシュと ISR

Next.js は、レスポンス、生成された静的ページ、ビルド出力、および画像・フォント・スクリプトなどのその他の静的アセットをキャッシュできます。

ページのキャッシュと再検証（[Incremental Static Regeneration](/docs/app/guides/incremental-static-regeneration) を使用）は、**同じ共有キャッシュ** を利用します。デフォルトでは、このキャッシュは Next.js サーバー上のファイルシステム（ディスク）に保存されます。**これは Pages と App Router の両方でセルフホスティングしている場合に自動的に機能します。**

キャッシュされたページやデータを永続的なストレージに保持したり、複数のコンテナや Next.js アプリケーションのインスタンス間でキャッシュを共有したい場合は、Next.js のキャッシュの保存先を構成できます。

### 自動キャッシュ

- Next.js は、実際に変更されないアセットに対して `public, max-age=31536000, immutable` の `Cache-Control` ヘッダーを設定します。これは上書きできません。これらの immutable なファイルのファイル名には SHA ハッシュが含まれているため、無期限に安全にキャッシュできます。例として、[Static Image Imports](/docs/app/getting-started/images#local-images) があります。画像については、[TTL を設定](/docs/app/api-reference/components/image#minimumcachettl) できます。
- Incremental Static Regeneration (ISR) は `s-maxage: <revalidate in getStaticProps>, stale-while-revalidate` の `Cache-Control` ヘッダーを設定します。この再検証時間は、[`getStaticProps` 関数](/docs/pages/building-your-application/data-fetching/get-static-props) 内で秒数として定義します。`revalidate: false` を設定した場合、デフォルトで 1 年間のキャッシュ期間が適用されます。
- 動的にレンダリングされるページは、ユーザー固有のデータがキャッシュされないようにするために `private, no-cache, no-store, max-age=0, must-revalidate` の `Cache-Control` ヘッダーを設定します。これは App Router と Pages Router の両方に適用されます。また、[Draft Mode](/docs/app/guides/draft-mode) も含まれます。

### 静的アセット

静的アセットを別のドメインや CDN 上でホストしたい場合は、`next.config.js` の `assetPrefix` [設定](/docs/app/api-reference/config/next-config-js/assetPrefix)を使用できます。Next.js は JavaScript や CSS ファイルを取得する際に、このプレフィックスを使用します。アセットを別ドメインに分離すると、DNS および TLS の名前解決に追加の時間がかかるというデメリットがあります。

[`assetPrefix` の詳細はこちら](/docs/app/api-reference/config/next-config-js/assetPrefix)。

### キャッシュの設定

デフォルトでは、生成されたキャッシュアセットはメモリ（デフォルトで 50MB）およびディスクに保存されます。Kubernetes のようなコンテナオーケストレーションプラットフォームを使って Next.js をホスティングしている場合、各 Pod はキャッシュのコピーを持つことになります。デフォルトでは Pod 間でキャッシュが共有されないため、古いデータが表示されるのを防ぐには、キャッシュハンドラーを指定し、インメモリキャッシュを無効化するように Next.js のキャッシュを設定できます。

セルフホスティング時に ISR/Data Cache の保存場所を構成するには、`next.config.js` ファイルでカスタムハンドラーを設定します：

```jsx filename="next.config.js"
module.exports = {
  cacheHandler: require.resolve('./cache-handler.js'),
  cacheMaxMemorySize: 0, // デフォルトのインメモリキャッシュを無効化
}
```

次に、プロジェクトのルートに `cache-handler.js` を作成します。例えば次のようにします:

```jsx filename="cache-handler.js"
const cache = new Map()

module.exports = class CacheHandler {
  constructor(options) {
    this.options = options
  }

  async get(key) {
    // 永続ストレージなど、任意の場所に保存できます
    return cache.get(key)
  }

  async set(key, data, ctx) {
    // 永続ストレージなど、任意の場所に保存できます
    cache.set(key, {
      value: data,
      lastModified: Date.now(),
      tags: ctx.tags,
    })
  }

  async revalidateTag(tags) {
    // tags は文字列または文字列の配列です
    tags = [tags].flat()
    // キャッシュ内のすべてのエントリを反復処理します
    for (let [key, value] of cache) {
      // 値のタグに指定されたタグが含まれている場合、このエントリを削除します
      if (value.tags.some((tag) => tags.includes(tag))) {
        cache.delete(key)
      }
    }
  }

  // 次のリクエストの前にリセットされる、単一リクエスト向けの
  // 一時的なインメモリキャッシュが必要な場合は、このメソッドを利用できます
  resetRequestCache() {}
}
```

カスタムのキャッシュハンドラーを使用すると、Next.js アプリケーションをホストしているすべての Pod 間でキャッシュの一貫性を確保できます。たとえば、キャッシュされた値を [Redis](https://github.com/vercel/next.js/tree/canary/examples/cache-handler-redis) や AWS S3 など、任意の場所に保存できます。

> **補足:**
>
> - `revalidatePath` はキャッシュタグの上にある利便性のためのレイヤーです。`revalidatePath` を呼び出すと、指定されたページ用の特別なデフォルトタグを使って `revalidateTag` 関数が実行されます。

## ビルドキャッシュ

Next.js は、どのバージョンのアプリケーションが配信されているかを識別するために、`next build` 実行時に ID を生成します。同じビルドを使用して、複数のコンテナを起動する必要があります。

環境の各ステージごとに再ビルドしている場合、コンテナ間で共通して使用できる一貫したビルド ID を生成する必要があります。`next.config.js` で `generateBuildId` を使用してください。

```jsx filename="next.config.js"
module.exports = {
  generateBuildId: async () => {
    // 任意の値を指定できます。ここでは最新のgitハッシュを使用しています
    return process.env.GIT_HASH
  },
}
```

## 複数サーバーへのデプロイ

Next.js を複数のサーバーインスタンス（たとえば、ロードバランサー配下のコンテナ）で実行する場合、一貫した動作を確保するために考慮すべき追加事項があります。

### サーバー関数の暗号化キー

Next.js は、クライアントに送信する前に [サーバー関数](/docs/app/getting-started/updating-data) のクロージャー変数を暗号化します。デフォルトでは、ビルドごとに一意の暗号化キーが生成されます。

複数のサーバーインスタンスを実行する場合、すべてのインスタンスで同じ暗号化キーを使用する必要があります。そうしないと、あるインスタンスで暗号化されたサーバー関数を別のインスタンスで復号できず、「Failed to find Server Action」エラーが発生します。

`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 環境変数を使用して、固定の暗号化キーを設定します。キーは、有効な AES キー長（16、24、または 32 バイト）を持つ Base64 エンコードされた値である必要があります。Next.js はデフォルトで 32 バイトのキーを生成します。

```bash
NEXT_SERVER_ACTIONS_ENCRYPTION_KEY=your-generated-key next build
```

キーはビルド成果物に埋め込まれ、実行時に自動的に利用されます。詳細については、[Data Security ガイド](/docs/app/guides/data-security#overwriting-encryption-keys-advanced)を参照してください。

### デプロイメント識別子

ローリングデプロイ中のバージョンずれ保護を有効にするには、[`deploymentId`](/docs/app/api-reference/config/next-config-js/deploymentId) を設定します。これにより、クライアントは常に同一のデプロイメントバージョンからアセットを取得できるようになります。

### 共有キャッシュ

デフォルトでは、Next.js はインスタンス間で共有されないインメモリキャッシュを使用します。一貫したキャッシュ動作を保証するには、外部ストレージにデータを保存する[カスタムキャッシュハンドラー](/docs/app/api-reference/config/next-config-js/cacheHandlers)と組み合わせて、[`'use cache: remote'`](/docs/app/api-reference/directives/use-cache-remote) を使用してください。

## バージョンのずれ

複数インスタンス構成でのセルフホスティングやローリングデプロイを行う場合、[version skew](/docs/app/glossary#version-skew) によって次のような問題が発生する可能性があります:

- **アセットの欠落**: クライアントが、サーバー上にもう存在しない JavaScript や CSS ファイルをリクエストする
- **Server Function の不一致**: クライアントが、以前のビルドの ID を使って Server Function を呼び出し、サーバー側でその ID が認識されない
- **ナビゲーションの失敗**: 古いデプロイからプリフェッチされたページデータが、新しいサーバーと互換性がない

Next.js は [`deploymentId`](/docs/app/api-reference/config/next-config-js/deploymentId) を使ってバージョンのずれを検出・処理します。デプロイメント ID が設定されている場合:

- 静的アセットには `?dpl=<deploymentId>` クエリパラメータが含まれる
- クライアントサイドナビゲーションのリクエストには `x-deployment-id` ヘッダーが含まれる
- サーバーはクライアントのデプロイメント ID を自身のものと比較する

不一致が検出された場合、Next.js はクライアントサイドナビゲーションの代わりにハードナビゲーション（ページ全体の再読み込み）をトリガーします。これにより、クライアントは同一のデプロイメントバージョンからアセットを取得できるようになります。

```js filename="next.config.js"
module.exports = {
  deploymentId: process.env.DEPLOYMENT_VERSION,
}
```

> **補足:** アプリケーションをリロードすると、ページ間のナビゲーションをまたいで状態が保持されるように設計されていない場合、アプリケーションの状態が失われる可能性があります。URL の状態やローカルストレージの内容は保持されますが、`useState` のようなコンポーネントの状態は失われます。

  ## Streaming と Suspense

Next.js の App Router は、セルフホスティングしている場合に [ストリーミングレスポンス](/docs/app/api-reference/file-conventions/loading) をサポートします。nginx や同様のプロキシを使用している場合は、ストリーミングを有効にするためにバッファリングを無効化するように設定する必要があります。

たとえば、nginx では `X-Accel-Buffering` を `no` に設定することでバッファリングを無効化できます:

```js filename="next.config.js"
module.exports = {
  async headers() {
    return [
      {
        source: '/:path*{/}?',
        headers: [
          {
            key: 'X-Accel-Buffering',
            value: 'no',
          },
        ],
      },
    ]
  },
}
```

## Cache Components

[Cache Components](/docs/app/getting-started/cache-components) は、CDN 専用の機能ではなく、Next.js でデフォルト有効になっています。これは、Node.js サーバーとしてのデプロイ (`next start` による起動) や、Docker コンテナと組み合わせて使用する場合も含まれます。

## CDN との併用

Next.js アプリケーションの前段に CDN を使用している場合、動的な API にアクセスすると、ページには `Cache-Control: private` レスポンスヘッダーが含まれます。これにより、生成された HTML ページがキャッシュ不可としてマークされます。ページが完全に静的にプリレンダリングされている場合は、CDN 上でのキャッシュを許可するために `Cache-Control: public` が含まれます。

静的コンポーネントと動的コンポーネントの両方を混在させる必要がない場合は、ルート全体を静的にし、出力された HTML を CDN にキャッシュさせることができます。この自動静的最適化は、動的 API が使用されていない場合に `next build` 実行時のデフォルトの挙動です。

Partial Prerendering が stable になるにつれ、Deployment Adapters API を通じてサポートを提供する予定です。

<AppOnly>
  ## `after`

[`after`](/docs/app/api-reference/functions/after) は、`next start` を用いたセルフホスティング環境で完全にサポートされています。

サーバーを停止する際は、`SIGINT` または `SIGTERM` シグナルを送信して待機することで、グレースフルシャットダウンを行ってください。これにより、Next.js サーバーは、`after` の内部で使用されている保留中のコールバック関数や Promise が完了するまで待機できます。

</AppOnly>

<PagesOnly>
  ## 手動でのグレースフルシャットダウン

セルフホスト時に、`SIGTERM` または `SIGINT` シグナルでサーバーがシャットダウンする際にコードを実行したい場合があります。

環境変数 `NEXT_MANUAL_SIG_HANDLE` を `true` に設定し、そのシグナル用のハンドラーを `_document.js` ファイル内で登録できます。環境変数は `.env` ファイルではなく、`package.json` の script 内で直接登録する必要があります。

> **補足**: 手動でのシグナル処理は `next dev` では利用できません。

```json filename="package.json"
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "NEXT_MANUAL_SIG_HANDLE=true next start"
  }
}
```

```js filename="pages/_document.js"
if (process.env.NEXT_MANUAL_SIG_HANDLE) {
  process.on('SIGTERM', () => {
    console.log('Received SIGTERM: cleaning up')
    process.exit(0)
  })
  process.on('SIGINT', () => {
    console.log('Received SIGINT: cleaning up')
    process.exit(0)
  })
}
```

</PagesOnly>
