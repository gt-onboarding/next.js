Next.js には `v10.0.0` 以降、国際化対応（[i18n](https://en.wikipedia.org/wiki/Internationalization_and_localization#Naming)）ルーティングのサポートが組み込まれています。ロケールの一覧、デフォルトロケール、およびドメイン固有のロケールを指定すると、Next.js が自動的にルーティングを処理します。

i18n ルーティングのサポートは現在、[`react-intl`](https://formatjs.io/docs/getting-started/installation)、[`react-i18next`](https://react.i18next.com/)、[`lingui`](https://lingui.dev/)、[`rosetta`](https://github.com/lukeed/rosetta)、[`next-intl`](https://github.com/amannn/next-intl)、[`next-translate`](https://github.com/aralroca/next-translate)、[`next-multilingual`](https://github.com/Avansai/next-multilingual)、[`tolgee`](https://tolgee.io/integrations/next)、[`paraglide-next`](https://inlang.com/m/osslbuzt/paraglide-next-i18n)、[`next-intlayer`](https://intlayer.org/doc/environment/nextjs/next-with-page-router)、[`gt-react`](https://generaltranslation.com/en/docs/react) などの既存の i18n ライブラリソリューションを補完することを目的としており、ルートやロケールのパース処理を簡素化します。

## はじめに

まず、`next.config.js` ファイルに `i18n` 設定を追加します。

ロケールは [UTS Locale Identifiers](https://www.unicode.org/reports/tr35/tr35-59/tr35.html#Identifiers) に準拠しており、ロケールを定義するための標準化されたフォーマットです。

一般的にロケール識別子は、ハイフンで区切られた言語・地域・スクリプトで構成されます: `language-region-script`。地域とスクリプトは省略可能です。例:

- `en-US` - アメリカ合衆国で話される英語
- `nl-NL` - オランダで話されるオランダ語
- `nl` - 地域を特定しないオランダ語

ユーザーのロケールが `nl-BE` で、それが設定に含まれていない場合、`nl` が定義されていればそのロケールに、定義されていなければデフォルトロケールにリダイレクトされます。
特定の国のすべての地域をサポートする予定がない場合、その国の言語ロケールをフォールバックとして含めておくことは良いプラクティスです。

```js filename="next.config.js"
module.exports = {
  i18n: {
    // アプリケーションでサポートしたいすべてのロケール
    locales: ['en-US', 'fr', 'nl-NL'],
    // ロケールプレフィックスのないパス（例: `/hello`）にアクセスした際に
    // 使用されるデフォルトロケール
    defaultLocale: 'en-US',
    // ロケールドメインとそのデフォルトロケールのリスト
    // （ドメインルーティングを設定する場合のみ必要）
    // 注意: サブドメインはドメインの値に含める必要があります（例: "fr.example.com"）
    domains: [
      {
        domain: 'example.com',
        defaultLocale: 'en-US',
      },
      {
        domain: 'example.nl',
        defaultLocale: 'nl-NL',
      },
      {
        domain: 'example.fr',
        defaultLocale: 'fr',
        // オプションの http フィールドを使用して、
        // https の代わりに http でロケールドメインをローカルテストすることもできます
        http: true,
      },
    ],
  },
}
```

## ロケール戦略

ロケールの処理には、サブパスルーティングとドメインルーティングという 2 つの戦略があります。

### サブパスルーティング

サブパスルーティングでは、ロケールを URL のパスに含めます。

```js filename="next.config.js"
module.exports = {
  i18n: {
    locales: ['en-US', 'fr', 'nl-NL'],
    defaultLocale: 'en-US',
  },
}
```

上記の設定では、`en-US`、`fr`、`nl-NL` をルーティング先として利用できるようになり、`en-US` がデフォルトロケールになります。`pages/blog.js` がある場合、次の URL が利用可能です:

- `/blog`
- `/fr/blog`
- `/nl-nl/blog`

デフォルトロケールにはプレフィックスは付きません。

### ドメインルーティング

ドメインルーティングを使用すると、ロケールを異なるドメインから提供するように設定できます。

```js filename="next.config.js"
module.exports = {
  i18n: {
    locales: ['en-US', 'fr', 'nl-NL', 'nl-BE'],
    defaultLocale: 'en-US',

    domains: [
      {
        // 注意: サブドメインはドメインの値に含める必要があります
        // 例: 期待されるホスト名が www.example.com の場合、それを使用する必要があります
        domain: 'example.com',
        defaultLocale: 'en-US',
      },
      {
        domain: 'example.fr',
        defaultLocale: 'fr',
      },
      {
        domain: 'example.nl',
        defaultLocale: 'nl-NL',
        // このドメインにリダイレクトされるべき
        // 他のロケールを指定する
        locales: ['nl-BE'],
      },
    ],
  },
}
```

例えば、`pages/blog.js` がある場合、次の URL にアクセスできるようになります:

- `example.com/blog`
- `www.example.com/blog`
- `example.fr/blog`
- `example.nl/blog`
- `example.nl/nl-BE/blog`

## 自動ロケール検出

ユーザーがアプリケーションのルート（一般的には `/`）にアクセスすると、Next.js は [`Accept-Language`](https://developer.mozilla.org/docs/Web/HTTP/Headers/Accept-Language) ヘッダーと現在のドメインに基づいて、ユーザーが希望するロケールを自動的に検出しようとします。

デフォルトのロケール以外のロケールが検出された場合、ユーザーは次のいずれかにリダイレクトされます:

- **サブパスルーティングを使用している場合:** ロケールのプレフィックス付きパス
- **ドメインルーティングを使用している場合:** そのロケールをデフォルトとして指定しているドメイン

ドメインルーティングを使用している場合、`Accept-Language` ヘッダーが `fr;q=0.9` のユーザーが `example.com` にアクセスすると、そのドメインが `fr` ロケールをデフォルトで扱うため、`example.fr` にリダイレクトされます。

サブパスルーティングを使用している場合、ユーザーは `/fr` にリダイレクトされます。

### デフォルトロケールへのプレフィックス付与

Next.js 12 と [Proxy](/docs/pages/api-reference/file-conventions/proxy) を使用すると、[ワークアラウンド](https://github.com/vercel/next.js/discussions/18419) によってデフォルトロケールにプレフィックスを付けることができます。

たとえば、いくつかの言語をサポートする `next.config.js` ファイルは次のようになります。`"default"` ロケールが意図的に追加されていることに注意してください。

```js filename="next.config.js"
module.exports = {
  i18n: {
    locales: ['default', 'en', 'de', 'fr'],
    defaultLocale: 'default',
    localeDetection: false,
  },
  trailingSlash: true,
}
```

次に、[Proxy](/docs/pages/api-reference/file-conventions/proxy) を使ってカスタムルーティングルールを追加できます。

```ts filename="proxy.ts"
import { NextRequest, NextResponse } from 'next/server'

const PUBLIC_FILE = /\.(.*)$/

export async function proxy(req: NextRequest) {
  if (
    req.nextUrl.pathname.startsWith('/_next') ||
    req.nextUrl.pathname.includes('/api/') ||
    PUBLIC_FILE.test(req.nextUrl.pathname)
  ) {
    return
  }

  if (req.nextUrl.locale === 'default') {
    const locale = req.cookies.get('NEXT_LOCALE')?.value || 'en'

    return NextResponse.redirect(
      new URL(`/${locale}${req.nextUrl.pathname}${req.nextUrl.search}`, req.url)
    )
  }
}
```

この [Proxy](/docs/pages/api-reference/file-conventions/proxy) は、[API Routes](/docs/pages/building-your-application/routing/api-routes) やフォント・画像などの [public](/docs/pages/api-reference/file-conventions/public-folder) ファイルに対して、デフォルトのプレフィックスを追加しません。リクエストがデフォルトロケールに対して行われた場合は、`/en` プレフィックス付きのパスへリダイレクトします。

### 自動ロケール検出を無効にする

自動ロケール検出機能は次のように無効化できます:

```js filename="next.config.js"
module.exports = {
  i18n: {
    localeDetection: false,
  },
}
```

`localeDetection` が `false` に設定されている場合、Next.js はユーザーの優先ロケールに基づいて自動的にリダイレクトしなくなり、上で説明したロケールベースのドメインまたはロケールパスから検出されたロケール情報のみを使用します。

## ロケール情報へのアクセス

Next.js のルーター経由でロケール情報にアクセスできます。たとえば、[`useRouter()`](/docs/pages/api-reference/functions/use-router) フックを使用すると、次のプロパティが利用可能です:

- `locale` には現在アクティブなロケールが含まれます。
- `locales` には設定されているすべてのロケールが含まれます。
- `defaultLocale` には設定されているデフォルトロケールが含まれます。

`getStaticProps` または `getServerSideProps` を使用してページを[プリレンダリング](/docs/pages/building-your-application/rendering/static-site-generation)する場合、ロケール情報は関数に渡される[コンテキスト](/docs/pages/building-your-application/data-fetching/get-static-props)内で提供されます。

`getStaticPaths` を利用する場合、設定されているロケールは関数のコンテキスト引数内の `locales` に、設定されているデフォルトロケールは `defaultLocale` にそれぞれ含まれます。

## ロケール間の遷移

ロケール間を遷移するには、`next/link` または `next/router` を使用できます。

`next/link` の場合、現在アクティブなロケールとは異なるロケールへ遷移するために `locale` プロップを指定できます。`locale` プロップが指定されていない場合、クライアントサイドでの遷移時には現在アクティブな `locale` が使用されます。たとえば、次のようになります。

```jsx
import Link from 'next/link'

export default function IndexPage(props) {
  return (
    <Link href="/another" locale="fr">
      To /fr/another
    </Link>
  )
}
```

`next/router` のメソッドを直接使用する場合は、遷移オプションで使用する `locale` を指定できます。例えば次のようになります。

```jsx
import { useRouter } from 'next/router'

export default function IndexPage(props) {
  const router = useRouter()

  return (
    <div
      onClick={() => {
        router.push('/another', '/another', { locale: 'fr' })
      }}
    >
      to /fr/another
    </div>
  )
}
```

なお、`locale` のみを切り替えつつ、[動的ルート](/docs/pages/building-your-application/routing/dynamic-routes)のクエリ値や非表示の href クエリ値など、すべてのルーティング情報を保持したい場合は、`href` パラメータをオブジェクトとして指定できます。

```jsx
import { useRouter } from 'next/router'
const router = useRouter()
const { pathname, asPath, query } = router
// ロケールだけを変更し、hrefのクエリを含む他のすべてのルート情報を維持する
router.push({ pathname, query }, asPath, { locale: nextLocale })
```

`router.push` に渡すオブジェクトの構造の詳細については[こちら](/docs/pages/api-reference/functions/use-router#with-url-object)を参照してください。

すでにロケールを含む `href` を持っている場合は、ロケールのプレフィックスを自動で付与する動作を無効化できます:

```jsx
import Link from 'next/link'

export default function IndexPage(props) {
  return (
    <Link href="/fr/another" locale={false}>
      To /fr/another
    </Link>
  )
}
```

## `NEXT_LOCALE` Cookie の活用

Next.js では、`NEXT_LOCALE=the-locale` Cookie を設定でき、この Cookie は `accept-language` ヘッダーよりも優先されます。言語切り替え UI などを使ってこの Cookie を設定しておくと、ユーザーがサイトに戻ってきた際、`/` から対応するロケールのパスへリダイレクトする際に、その Cookie で指定されたロケールが使用されます。

たとえば、ユーザーの `accept-language` ヘッダーではロケールとして `fr` が優先されていても、`NEXT_LOCALE=en` Cookie が設定されている場合、ユーザーが `/` にアクセスすると `en` ロケールのパスにリダイレクトされます。この動作は、Cookie が削除されるか有効期限が切れるまで続きます。

## 検索エンジン最適化

Next.js はユーザーがどの言語でページを閲覧しているかを判別できるため、自動的に `<html>` タグに `lang` 属性を追加します。

Next.js はページのバリエーションについては認識していないため、`hreflang` メタタグは [`next/head`](/docs/pages/api-reference/components/head) を使って開発者側で追加する必要があります。`hreflang` について詳しくは、[Google Webmasters のドキュメント](https://support.google.com/webmasters/answer/189077)を参照してください。

## 静的生成ではどのように動作しますか？

> Internationalized Routing は Next.js のルーティングレイヤーを利用しないため、[`output: 'export'`](/docs/pages/guides/static-exports) とは連携しないことに注意してください。`output: 'export'` を使用しないハイブリッド構成の Next.js アプリケーションは、完全にサポートされています。

### 動的ルートと `getStaticProps` ページ

`getStaticProps` と[動的ルート](/docs/pages/building-your-application/routing/dynamic-routes)を使用するページでは、事前レンダリングしたいページの、すべてのロケールごとのバリエーションを [`getStaticPaths`](/docs/pages/building-your-application/data-fetching/get-static-paths) から返す必要があります。`paths` に対して返される `params` オブジェクトに加えて、どのロケールをレンダリングするかを指定する `locale` フィールドも返すことができます。たとえば次のようになります。

```jsx filename="pages/blog/[slug].js"
export const getStaticPaths = ({ locales }) => {
  return {
    paths: [
      // `locale` が指定されていない場合、defaultLocaleのみが生成される
      { params: { slug: 'post-1' }, locale: 'en-US' },
      { params: { slug: 'post-1' }, locale: 'fr' },
    ],
    fallback: true,
  }
}
```

[Automatically Statically Optimized](/docs/pages/building-your-application/rendering/automatic-static-optimization) なページと、非動的な `getStaticProps` ページについては、**各ロケールごとにページのバージョンが生成されます**。これは、`getStaticProps` 内で設定されているロケール数によってはビルド時間が増加する可能性があるため、考慮する必要があります。

たとえば、50 個のロケールが設定されていて、`getStaticProps` を使用する非動的ページが 10 ページある場合、`getStaticProps` は合計 500 回呼び出されます。各ビルドで 10 ページそれぞれについて 50 個のバージョンが生成されることになります。

`getStaticProps` を使った動的ページのビルド時間を短縮するには、[`fallback` モード](/docs/pages/api-reference/functions/get-static-paths#fallback-true) を使用します。これにより、ビルド時にプリレンダリングするために、`getStaticPaths` から最もよく利用されるパスとロケールだけを返せるようになります。その後、Next.js はリクエストに応じて残りのページを実行時にビルドします。

### 自動静的最適化されるページ

[自動静的最適化](/docs/pages/building-your-application/rendering/automatic-static-optimization) が有効なページでは、各ロケールごとにページのバージョンが生成されます。

### 非動的な getStaticProps ページ

非動的な `getStaticProps` ページでは、上記と同様に各ロケールごとにバージョンが生成されます。`getStaticProps` は、レンダリングされるそれぞれの `locale` を引数に呼び出されます。特定のロケールを事前レンダリングの対象から外したい場合は、`getStaticProps` から `notFound: true` を返すことで、そのロケール向けのページは生成されません。

```js
export async function getStaticProps({ locale }) {
  // 外部APIエンドポイントを呼び出して投稿を取得する。
  // 任意のデータ取得ライブラリを使用できる
  const res = await fetch(`https://.../posts?locale=${locale}`)
  const posts = await res.json()

  if (posts.length === 0) {
    return {
      notFound: true,
    }
  }

  // { props: posts } を返すことで、Blog コンポーネントは
  // ビルド時に `posts` をプロップとして受け取る
  return {
    props: {
      posts,
    },
  }
}
```

## i18n 設定の制限

- `locales`: 合計 100 個まで
- `domains`: ロケールドメイン項目 合計 100 個まで

> **補足**: これらの制限は、主に[ビルド時のパフォーマンス問題](#dynamic-routes-and-getstaticprops-pages)を防ぐために設けられています。Next.js 12 では、[Proxy](/docs/pages/api-reference/file-conventions/proxy) を使ったカスタムルーティングによって、これらの制限を回避できます。
